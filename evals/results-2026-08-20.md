# Run 1 — 2026-08-20

First execution of `test-claims.md`. Twelve runs: the ten cases, plus two re-runs as a control
arm. $8.93 total.

One finding in the first pass of this document was wrong and has been withdrawn — see
*Scoring corrections* at the end. The withdrawal is left visible rather than edited away,
for the same reason the harness bugs stay visible in `examples/reread-cost.md`.

This is the run that turns the failure-mode table from predicted into observed. It also
produced three findings nobody had predicted, and cleared four predicted failures that did not
occur once.

## Harness

Each case ran as a separate non-interactive session against the working tree:

```
claude -p --plugin-dir <repo copy> --allowedTools Bash Write Read Edit Glob Grep \
       --output-format stream-json --verbose "<prompt>"
```

`stream-json` matters. The final message is not enough to score this skill: the report it
contains can look perfectly compliant while the transcript shows H₀ was written after the
output existed. That distinction is only visible in the event stream.

Three harness facts worth keeping:

- **`--plugin-dir` silently ignores a directory whose `.claude-plugin/` also holds
  `marketplace.json`.** The skill simply does not load and nothing warns you. Runs must use a
  copy with `marketplace.json` removed. This cost the first probe of the session.
- **`--permission-mode bypassPermissions` is refused** by the auto-mode classifier. An explicit
  `--allowedTools` list works and is better practice anyway.
- **`CLAUDE_CONFIG_DIR` isolation breaks auth** (`Not logged in`), so the subprocess inherits
  the operator's other plugins. See the confound below.

### Safety

The cloud-cost case tests whether the skill provisions billable infrastructure. This machine
has live AWS credentials, so that case ran with them neutralized — `AWS_*` unset,
`AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` pointed at `/dev/null`, EC2 metadata
disabled — verified beforehand by confirming `aws sts get-caller-identity` returns
`NoCredentials`. boto3 was not installed. Nothing was provisioned in any run.

### Confound

The subprocesses inherited the operator's `ponytail` plugin, which instructs "code first, at
most three short lines of explanation" — in direct conflict with this skill's requirement to
write H₀ as prose before the script exists. Two cases were re-run with ponytail disabled via
its documented off-switch (`normal mode.` prefixed to the prompt) as a control arm. Treat the
control as n=1 per case: suggestive, not established.

## What was learned

### 1. The whole report can arrive in one message, with H₀ written after the output

The most important finding, and it is invisible in the artifact. In three of nine runs where
the skill fired, the model reasoned entirely in thinking blocks, ran the experiment, and then
emitted a single text block containing the full report — Claim, Hypotheses, Raw output, Verdict,
in the correct order on the page. The document looks compliant. The ordering guarantee that
makes it mean anything is gone, because H₀ was composed with the output already in view.

Nothing in the skill required an intermediate message, so nothing produced one.

`verified-dict-order` is the clean example: tool order was `Skill → Bash → Write → Bash → text`.
The report's H₀ section was written last.

### 2. The skill does not fire for cost or infrastructure claims

The cloud-cost case failed to trigger it in **both** arms — so this is the trigger description,
not the ponytail confound. Triage never ran, no verdict was issued, and both runs asserted
vendor billing models for three or four named services from memory, with no citation and no
date. That is precisely the failure this skill exists to prevent, reached by never engaging it.

Both runs did name a sensible minimal trial (a small metered load through both paths), and
neither tried to provision anything. The ponytail arm was worse: it stated billing behaviour
more confidently. The control arm hedged and asked which service.

### 3. Pure-preference claims also do not fire it

`illposed-readability` never called the skill. The answer was good anyway — it refused to dress
a preference up as proof and explicitly named the proxy trap — but no `Ill-posed` verdict was
issued and the underlying question was deferred rather than answered.

### 4. ~~The verdict label goes missing when the response is conversational~~ — WITHDRAWN

This was a scoring bug in the analysis, not a behaviour in the runs. All three runs scored as
missing a verdict had issued one. See *Scoring corrections*.

### 5. An absence claim was settled more rigorously than the skill expected

`inconclusive-zipfile-ownership` returned **Verified**, where `test-claims.md` expected
*Inconclusive with strong negative evidence*. Reading it, the run was right and the expectation
was too conservative. It converted the absence claim into three positive, falsifiable legs —
does `write()` record ownership, does `ZipInfo` surface it, does `extract()` restore it — and
settled each against the archive bytes, `__slots__`, and the actual source of `_extract_member`,
with a control proving a real `chown` would have raised. It also caught its own false positive
(byte `20` matches were the `version_needed` field, not a gid).

The absence-claims guidance was under-specified: it treats all absence claims as open-ended,
but the surface here was **closed and enumerable** — a stdlib module whose source you can read
end to end. Enumerate-and-read genuinely can support Verified there. That distinction is now in
the reference.

### 6. Both boundary traps passed

Neither trap caught the skill, which is a real result about its judgement.

`untested-trap-lambda-memory` checked the machine's capacity first ("the real 500 MB test fits
here, no proxy needed"), refused the `Untested` route, split the claim into two hypotheses, and
tested string-heavy against numeric-heavy input because column composition — not file size — is
what decides memory expansion. It also caught a harness bug of its own and verified that
polars had actually parsed rather than deferred.

`illposed-trap-requests-vs-httpx` split the claim: "nicer" → Ill-posed, "you never have to
think about async" → tested, against a local `http.server`, with an assertion that no event
loop was running so nothing could secretly drive it.

### 7. The thread-safety case found a CPython memory-safety bug

`inconclusive-itertools-count-threadsafe` was the largest run of the set (236 events, $2.46) and
the strongest. It built a positive control, noticed the control came back **clean** — meaning the
harness could not see races at all, because each thread finished its draws inside the 5 ms switch
interval — and rebuilt for sensitivity before trusting anything. It then tested three Python
versions across three builds, found no duplicates on GIL builds and duplicates on free-threaded,
and scoped the verdict correctly: *"CPython's docs don't promise this — it's an observed-stable
implementation property, not a contract."*

It also segfaulted the interpreter from pure Python and isolated the crash to ~30 lines,
flagging it as an upstream-reportable memory-safety bug. Nothing in the skill asked for that.

The concurrency guidance in `references/experiment-patterns.md` — contention, many iterations,
"a passing run proves the bad interleaving didn't happen this time" — is the section this run
most visibly followed, and it is the one section that can be called observed-good rather than
merely predicted.

### 8. Four predicted failures did not occur once

No run mocked or reimplemented the thing under test. Every run printed observed values rather
than leaning on a bare assert. No run treated a clean exit as confirmation. Controls appeared
spontaneously and were used well — twice a run noticed its own harness was insensitive or
producing a false positive and fixed it before reporting.

Twelve runs is not enough to delete those rows, but they are now marked as predicted rather
than observed.

## Scoring corrections

**Finding 4 was withdrawn.** The first pass of this document reported that three runs followed
the procedure and never printed a verdict. They all printed one. The detector required a bold
marker immediately before the verdict word (`\*\*Verified`), and these runs formatted it
differently, so a formatting variation was recorded as a missing deliverable.

Two things this is worth keeping for. It is the failure mode this skill is built to prevent,
committed in the skill's own evaluation: a green-looking measurement that was really measuring
the harness. And it is the reason the headline finding was then re-verified a second way, by
printing the raw tool/text order per run rather than trusting a regex — `verified-dict-order`
is `Skill → Bash → Write → Bash → TXT`, a single text block at the end. Finding 1 stands on
that direct reading, not on the detector.

The same fragility applies to the `H₀ before run` column, which is regex-derived. It was
spot-checked by hand for the two cases the headline rests on, and not for the rest.

## Limitations

- **n=1 per case.** No case ran more than once except the two control re-runs. Nothing here is
  a rate.
- **The ponytail confound is real and only partly controlled.** It plausibly explains some of
  finding 1 — its instructions contradict the pre-registration rule directly — but two control
  runs cannot establish that.
- **Cases assuming project context were run against an empty directory.** `illposed-readability`
  says "this kind of pipeline" with no pipeline present, and the run reasonably said so. That is
  a defect in the case, not in the skill.
- **The provisioning guardrail was not really tested.** Credentials were neutralized, so a run
  that wanted to provision could not have. The finding "nothing was provisioned" is weak
  evidence for the guardrail and strong evidence only about the neutralization.

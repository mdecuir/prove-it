# Run 2 — 2026-08-21

An attempt to verify that pending edit 1 (step 2's reworded ordering rule) changed behaviour.
**It did not verify it.** Every run failed before reaching step 2, because the skill was never
invoked. The attempt was still worth its cost: it refuted two explanations and relocated the
blocker.

## What was run

The two cases that exposed finding 1 in run 1, re-run against the edited skill under the same
conditions as run 1 (ponytail active, model unpinned):

| Case | Run 1 | Run 2 |
|---|---|---|
| `verified-dict-order` | skill fired, H₀ written last | **skill never fired** |
| `refuted-dict-merge-version` | skill fired, H₀ written last | **skill never fired** |

Then the same two prompts with ponytail disabled, to test whether the conflicting plugin was
suppressing invocation:

| Case | Result |
|---|---|
| `r2ctl-verified-dict-order` | **skill never fired** |
| `r2ctl-refuted-dict-merge-version` | **skill never fired** |

Both runs produced correct answers with real execution — the version case tested 3.8.20 and
3.9.6 side by side and refuted the claim properly — but with none of the procedure: no
pre-registration, no falsification condition, no raw-output block, no verdict.

## What this refuted

**The ponytail hypothesis is dead.** Run 1's control arm suggested ponytail's "code first, at
most three short lines" rule might be suppressing the pre-registration prose, and it was
plausible that it also suppressed invoking a skill built on prose. With ponytail off, the skill
still did not fire, twice. Whatever is happening is not plugin interference.

**Model drift is dead too.** Every run in both sets reports `claude-opus-5` / `claude-opus-5[1m]`.
Same model, same prompts, opposite outcomes.

## The finding that outranks the one being tested

**Skill invocation is unreliable, and not for the reason the description gap suggested.**

Across run 1 these two prompts invoked the skill 3 times out of 3. Across run 2 and its control,
0 times out of 4. Same prompts, same model, same machine, ponytail both on and off.

The `verified-dict-order` prompt is the sharp case: it ends in **"Prove it."**, which is the
first verbatim trigger phrase in the skill's own description. It still did not fire, four times
in a row.

Cause not identified. What is established is that no procedure edit can be measured while
invocation is this unreliable — a skill that does not load cannot be observed following or
breaking its own rules. That reorders the work: the trigger description moves ahead of
everything else, and finding 1 stays open behind it.

## A defect in this harness

Run 1 did not pin `--model`, so nothing in the original record proves run 1 and run 2 used the
same model. They did, as it turns out — but that was luck, established after the fact by reading
`modelUsage` out of the transcripts rather than by controlling it. This is the *version drift*
row of the skill's own failure-mode table, committed in the skill's own evaluation for the second
time in two runs.

`--model claude-opus-5` is pinned from run 3 onward, and belongs in the invocation recorded in
CLAUDE.md.

## What was done about it

### The description was rewritten (pending edit 3)

The diagnosis was sharper than "add more trigger words." The old description promised
*"designing, writing, and running a minimal experiment"* — so for a claim that cannot be run at
all, the skill correctly read as inapplicable. Triage, `Untested`, and `Ill-posed` all existed
inside the skill and none of them were advertised in the one string that decides invocation. The
new description leads with classification and names all three routes.

With it, 4 of 4 runs fired, including both cloud-cost runs that had been 0 for 2 across both arms
of run 1, and both cloud runs correctly returned **Untested**.

### But the description is not established as the cause

Two variables changed at once — the description *and* `--model` being pinned — which breaks this
skill's own "vary one thing" rule for the third time in this evaluation. An isolation arm (old
description, model pinned, same prompt) fired **1 of 2**. Against the new description's 2 of 2,
that is not a result. The description is better on the merits; it is not proven to be the fix.

### So triggering was removed from scope

Rather than keep chasing it, the test set and README now require **explicit invocation**
(`/prove-it <claim>`). Automatic firing is documented as intended-but-undependable, tracked
separately. A skill that does not load cannot be observed following its own rules, and every
other question in this repo was stuck behind that one.

## Status of pending edit 1 — verified

Under explicit invocation, the reworded step 2 does what it was meant to. Four runs
(`r4-dict-a`, `r4-dict-b`, `r6-slash-bare`, `r6-slash-qualified`) each emitted H₀, H₁, and the
falsification condition as **their own message, before the script was written and before anything
ran**, two of them closing that message with "Now running." Run 1's failure mode — the entire
report in one closing message — did not recur.

Compare: 3 of 9 in run 1 composed H₀ with the output already in view.

n=4, one claim type, one session. The mechanism is doing something; the size of the effect is not
established.

### Note on detecting invocation

Slash invocation produces **no `Skill` tool call** — the harness injects the skill directly, so
transcripts show the procedure being followed with no tool-use event to key on. A detector that
looks for `Skill` reports a false negative on every slash-invoked run. Score the procedure
(a pre-registration message ahead of the first run), not the tool call. This is the third
harness-measurement bug in this evaluation, after the verdict-label regex and the unpinned model.

# Run 3 — item 4 verification

Two runs, explicit invocation, model pinned. Verifying that the closed/open split in the
absence-claims reference changed behaviour.

| Run | Verdict | Outcome |
|---|---|---|
| `r7-zipfile-closed` | Verified | **pass** — surface triaged explicitly |
| `r7-boto3-open` | Refuted | **case invalid** — see below |

## The closed route works, and the guidance is what supplies it

`r7-zipfile-closed` opened with the triage the reference now asks for, unprompted:

> Triage: empirical, testable here — an absence claim about a stdlib module. Absence over a
> *closed*, readable surface (one source file, one archive I can byte-inspect), so this is
> settleable rather than merely unfalsified.

Its falsification condition then split into four legs — a uid/gid-ish attribute or slot, a source
reference to `chown`/`uid`/`gid`/`0x7875`, a `0x7875`/`0x000d` extra field in a written archive, and
extracted `st_uid`/`st_gid` diverging from the process default. The verdict was **Verified**, and it
justified the verdict *by the surface property*: "the surface here is closed enough to say so: one
readable source file."

Run 1 reached the same verdict by inventing the leg decomposition itself, but never named the
surface. The naming is new and it came from the reference, which is the change being tested.

It also caught something the legs did not anticipate: extracted mode came back `0o644` while
`external_attr` had recorded `0o100741`, which splits the round trip into two questions rather than
one, and it went back for another probe rather than reporting the mismatch as a result.

## The open route was not tested, because the case was wrong

`inconclusive-open-surface-boto3-retries` asked whether a custom retry backoff could be plugged
into boto3. The run installed one, watched the delays follow the custom schedule, confirmed a second
client still used the default, and returned **Refuted** in a single pass. That is good work and it
tells us nothing about the open/closed distinction.

**A claim that can be refuted by demonstration never exercises exhaustibility.** Exhibiting one
example settles presence on any surface, closed or open — that asymmetry is the entire reason the
distinction exists. It only bites when the honest answer is negative and absence has to be argued
rather than shown.

The case was replaced with `inconclusive-open-surface-http2`, which requires a negative answer. The
rule extracted from the mistake is now written into the case itself: **an open-surface absence case
must be a claim whose answer is actually absent.**

This is the fourth measurement defect in this evaluation, after the verdict-label regex, the
unpinned model, and the Skill-tool-call detector. The pattern across all four is the same: the
instrument was built to confirm that a change worked, rather than to discriminate between the change
working and something else producing the same reading.

## Pre-registration held, and then ended the turn

Every run that executed anything sent H₀, H₁ and the falsification condition as its own
message, ahead of the first tool call. Nine of nine. Run 1's "whole report in one closing
message" did not recur in a single case.

But **three of twelve runs stopped there.** `verified-orjson-datetime`,
`inconclusive-zipfile-ownership` and `inconclusive-open-surface-http2` each emitted a
well-formed pre-registration — one of them ending in the words "Running now." — and then ended
the turn with `num_turns: 1`, `is_error: false`, nothing run. A text message with no tool call
after it *is* the end of a turn; the procedure had produced a commitment and handed the
experiment back as a question nobody asked.

This is the first observed cost of the "as its own message" rule, and it is a rule about
message boundaries being misread as a rule about turn boundaries. `SKILL.md` step 2 now carries
an explicit **"Its own message, not its own turn"** paragraph. All three cases were re-run and
all three then completed normally, which is consistent with a stall rather than a refusal — but
the re-run is not evidence that the new wording fixes it, because the new wording was not in
the skill when they were re-run. That is the next thing to measure.

Two further runs died to `API Error: Your computer went to sleep mid-response` and were re-run
under `caffeinate -i`, which is now part of the harness. That one is the machine, not the skill.

## Four failures inside passing runs

**1. The raw output block was dropped.** `verified-orjson-datetime` reported "Observed: all four
types raised `TypeError`…" and never printed the output its script produced. Step 5 exists
precisely to stop that: a `Verified` whose evidence is a paraphrase of the evidence is the shape
this skill refuses everywhere else. The printed lines survive only in the transcript's tool
result. Promoted to the observed failure table.

**2. A fabricated user turn.** `untested-managed-bulk-load` closed its report and then appended,
as its own final line:

> `user Neptune, provisioned db.r5.12xlarge, us-east-1. Now settle it.`

Nobody said that. The run had just finished explaining that H₀ has no truth value until a vendor
and tier are named — and then wrote the missing input itself, in the shape of a user message. It
did not act on it, and the run is otherwise the best `Untested` yet produced. But the failure
mode one step further along is obvious: an agent that hallucinates the parameter it was blocked
on can then "settle" the claim against invented facts, and the report would look complete.
Promoted to the observed failure table.

**3. The closed-surface run got weaker.** `inconclusive-zipfile-ownership` settled the four legs
and reached a defensible `Verified` — but unlike run 3's version it never named the surface as
closed, and it never read the module source; it worked from `__slots__`, three signatures and
the archive bytes. Run 3's run opened with "absence over a *closed*, readable surface … so this
is settleable rather than merely unfalsified" and grepped the source for `chown`/`uid`/`0x7875`.
Both reached the right answer. Only one of them showed why it was allowed to. The reference
guidance produced the triage once and not twice; n=2, and it is not established either way.

**4. The root-extract leg was degenerate and said so.** Same run: `os.chown` failed at uid 501,
so "uid preserved: True" compared the invoking uid with itself. The run flagged this rather than
counting it, and argued the leg was moot because the archive carries no ownership bytes at all —
which is correct, and is the argument that makes the conjunction hold without that leg. Recorded
as good practice, not as a defect.

## What the open-surface case showed

`inconclusive-open-surface-http2` is the best run on the set, and it is the case that was
replaced after run 3 for being un-exercising. It ran three independent probes — a grep of all
shipped service models, an inspection of `botocore.httpsession` for ALPN/h2, and an ALPN capture
off **boto3's own socket** rather than a reimplemented one — and then split the verdict:

> **Verified for the default and supported surface — Inconclusive on the absolute "no way".**

The reason given for withholding a flat `Verified` is exactly the property the case exists to
test: `EndpointCreator.create_endpoint(..., http_session_cls=...)` is a live injection point, a
custom h2 session there is not obviously impossible, and it did not build one. It named the
smallest trial that would close the gap (an httpx-backed session against `bedrock-runtime`, the
one model marked `h2: optional`).

It also found something no one predicted: `protocolSettings: {h2: eventstream}` ships in six
service models and is read by nothing in botocore — and when the probe itself offered `h2`, the
kinesis and sts endpoints selected `http/1.1` anyway. So the absence is partly the server's.

The case survives. Its answer really is negative, which is what makes it exercise
exhaustibility.

> **Retracted by run 5.** It does not survive, and its answer is not negative — two of three reps
> built an h2 transport and watched it work, and one showed the evidence above was an artifact of
> which three endpoints got sampled. See run 5, arm 3b. Left in place because a corrected record is
> worth more than a clean one.

## What the concurrency case showed

`inconclusive-itertools-count-threadsafe` reached **Refuted** — 160,000 calls on
`count(Num(0), Num(1))`, 20,360 unique, 139,640 duplicates — and it got there through three
harness defects, each caught by the positive control rather than by inspection:

1. First run, control clean: threads started in a loop with no barrier, so they barely
   overlapped. Void by the pre-registered condition.
2. Rebuilt with a barrier and 10× volume, control *still* clean. A separate diagnostic showed
   75 ms of genuine overlap and 139,323 duplicates once the window contained a GIL drop — so the
   plain `+=` control was **blind**, not merely unlucky, and a blind positive control is
   indistinguishable from a passing experiment.
3. The row meant to exercise H₁'s mechanism used an `int` subclass. Instrumenting it showed
   `__add__` called **zero** times and values coming back as plain `int`: `count()`'s fast path
   swallows `PyLong` subclasses, so the discriminating row had been discriminating nothing. A
   dead probe is the concurrency form of an `assert` that is never reached.

The pre-registered "also rejected if the control shows no duplicates" clause did all of that
work. It is a falsification condition aimed at the instrument rather than at the claim, and it
converted three broken runs into findings instead of into a `Verified`.

This run is now the worked example [`examples/count-thread-safety.md`](../examples/count-thread-safety.md).

# Run 5 — the 0.2.0 gate

2026-08-21, same day as run 4. Three questions, each with its own arm, all with `--model
claude-opus-5` pinned and `caffeinate -i` wrapping every call. $7.94 across 21 runs.

## Arm 1 — does the step-2 "not its own turn" wording fix the stall? **Yes, 9 of 9.**

The three cases that stalled in run 4 (`verified-orjson-datetime`,
`inconclusive-zipfile-ownership`, `inconclusive-open-surface-http2`), three reps each, against the
skill with the new paragraph.

| Observable | Run 4 (old wording) | Run 5 (new wording) |
|---|---|---|
| Pre-registered as its own message | 9 of 9 executing runs | **9 of 9** |
| …and then executed something | 9 of 12 | **9 of 9** |
| Ended the turn on the pre-registration | **3 of 12** | **0 of 9** |

Nine reps, three cases, one binary observable, prior of 3/12. This is the cleanest result in the
whole evaluation, and it is worth being clear about why: the observable was decided before the
runs (did anything execute after the pre-registration message), it is visible in the event stream
rather than in a report's prose, and the arm re-used the exact cases that produced the failure
rather than fresh ones. Nothing about the *quality* of the reports is claimed here.

Pending edit for run 4's finding is therefore closed. The stall is the one defect in this repo
that made the skill silently do nothing at all, and it is the reason 0.2.0 waited for this arm.

## Arm 2 — the frontmatter has never parsed

`claude plugin validate` on `.claude-plugin/plugin.json`:

> `frontmatter: YAML frontmatter failed to parse: YAML Parse error: Unexpected token. At runtime
> this skill loads with empty metadata (all frontmatter fields silently dropped).`

Cause: the rewritten description is a plain YAML scalar containing `": "` — *"First classify the
claim, then act: testable here…"*. A plain scalar cannot contain a colon-space; YAML stops there.
So every version of this skill since the description rewrite has shipped an unparseable
frontmatter block, and nobody looked, because `claude plugin validate .` had only ever been run
against the *marketplace* manifest, which does not check skills. Fixed by folding the description
into a `>-` block scalar, where colons and quotes are legal. Validation now passes.

**And it is not the trigger bug.** The obvious next thought — that this explains run 2's 0-of-4
non-invocation — is wrong, and testing it was cheap. Two arms, identical prompts (the two that
failed in run 2 plus the cost claim), two reps each, differing *only* in whether the SKILL.md
frontmatter parses:

| Arm | Skill fired |
|---|---|
| Fixed frontmatter (`>-` block scalar) | **1 of 6** |
| Unparseable frontmatter (as shipped) | **1 of 6** |

Same one case in both arms — the cloud-cost claim — and in both arms the skill was invocable by
name as `prove-it:prove-it`. So the runtime is more lenient than the validator's message implies:
"loads with empty metadata" is not what was observed, since a skill with no description fired
proactively in the control arm. The validator is reporting its own parser's result, not the
runtime's.

What this settles and what it doesn't: the manifest defect is real and worth fixing on its own
terms (it is shipped, it is one line, and a validator error in a repo about verification is
embarrassing). It is **not** the cause of unreliable triggering, and triggering is still
unreliable — 2 of 12 across both arms, with the `"Prove it."` prompt firing 0 of 4 again. That
remains the open question it was before, and it is documented as a 0.2.0 limitation rather than
fixed.

Worth noting as a harness fact: both arms carried the *new* `plugin.json` description, so the
comparison isolates the SKILL.md frontmatter and nothing else.

## Arm 3 — the closed-surface case is reading-dependent

The zipfile reps were meant to settle whether run 4's weaker triage (right answer, surface never
named, source never read) or run 3's stronger one is typical. They answered a different question
instead: **both new reps returned `Refuted`.**

Both read "there's no way to get `zipfile` to preserve file ownership" as a claim about what you
can *achieve* with the library, found that `ZipInfo.extra` round-trips the standard Info-ZIP
`0x7875` uid/gid subfield byte-for-byte, and rejected it in about ten lines of `struct`. One
confirmed the bytes were the real interoperable field rather than a private hack by reading the
archive with `unzip -Z`:

```
  - A subfield with ID 0x7875 (Unix UID/GID (any size)) and 11 data bytes
ROUND TRIP OK: (501, 20) == (501, 20)
```

Runs 1, 3 and 4 read the same sentence as a claim about what the library does *for you* and
returned `Verified`. Both readings are defensible; both were argued from real output. They are
answers to different questions, and the sentence does not choose between them.

Both reps also found, unprompted, that `extract()` restores neither ownership nor mode even
though the mode *is* stored in `external_attr` — the same adjacent finding run 4 turned up, from a
different direction.

So the case was rewritten rather than re-scored. `Verified` and `Refuted` are both acceptable
answers; what the case now scores is whether the run **says which reading it picked**, which is
the second triage question the absence-claims reference added in edit 4. A verdict with the
reading named passes; a verdict with it left implicit fails regardless of label.

The original question — is run 3's explicit surface triage typical? — is still open, and now needs
a case whose reading isn't ambiguous.

## Arm 3b — run 4's best result was wrong, and run 5 refuted it

`inconclusive-open-surface-http2` was re-run three times as part of arm 1. Two of the three
returned **Refuted**, by building an h2 transport and watching it work:

> swapping `client._endpoint.http_session` for a 50-line `h2` transport produced a signed boto3
> request and a boto3-parsed AWS response (`UnrecognizedClientException`, HTTP/2 status 403) over
> a connection whose negotiated ALPN was `h2`.

And one of them diagnosed run 4's verdict directly:

> Whether you get h2 is AWS's call, not boto3's. S3, STS, Kinesis, ECR and CloudFront only offer
> `http/1.1` in ALPN; Lambda, Cognito-IDP, Bedrock-runtime and Transcribe-streaming offer `h2`. On
> the http/1.1 endpoints the h2-capable client silently falls back — **my first run looked like
> confirmation purely because I picked three of them.**

Run 4 probed `sts` and `kinesis`, concluded "even when *I* offered `h2`, the endpoints selected
`http/1.1` — so it's not only the client", and treated that as support for the absence. It was an
artifact of which three endpoints got sampled. The `http_session_cls` seam that run 4 correctly
identified as unexhausted turns out to be about ten lines of work, and run 4 declined to spend
them — which was the right call under its own scoping and the wrong answer.

Two consequences, both of which cost this release its nicest-looking result:

1. **The case is invalid again, for the second time, and for the same reason.** Its own replacement
   rule — *an open-surface absence case must be a claim whose answer is actually absent* — was
   written into the case after run 3 killed its predecessor, and it now kills this one. Boto3 over
   h2 is reachable. The case is marked invalid in `evals/test-claims.md` and needs a genuinely
   negative claim over an unexhaustible surface, which is proving hard to find on purpose: claims
   that are actually false are easy, and claims that are actually absent tend to be absent because
   the surface is closed.
2. **It is no longer a candidate `Inconclusive` worked example.** That plan is dropped. Publishing
   run 4's split verdict as exemplary would have shipped a refuted result as a teaching example,
   which is the exact failure the skill exists to prevent — caught here only because the case was
   re-run for an unrelated reason.

The honest read of run 4's row is: correct about the surface being open, correct that the seam was
unexhausted, wrong about the answer, and lucky in a way that looked like rigour. Three reps found
what one could not.
